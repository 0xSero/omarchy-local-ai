The Local AI plan, explained

Written 2026-09-22 for Sero. Everything here comes from the repositories, GitHub and the machines as they were today. Sources: ~/local-omarchy/PROGRESS.md and omarchy-local-ai/docs/design.md.

In one sentence: turn the plugin into one script, one card and one data file that look like Omarchy wrote them, keep shipping that on the marketplace, and get it into Omarchy the way Omarchy actually accepts plugins, with a hundred-line PR, not a thousand-line one.

3. What I measured about Omarchy

You asked for this to be scientific and designed for dhh's repo. So instead of guessing, I measured the repo and its history.

QuestionFindingWhat it means for us
How big is a PR that gets merged?Last 200 merged PRs: median 57 added lines, 90th percentile 572. Everything over ~1,000 lines that merged was a release, a security fix, or written by a maintainer or their bot.A 1,000-line self-contained Local AI PR has no precedent. #10643 was bigger than any PR merged in 60 days.
Did a maintainer ever react to our six PRs?No. Zero comments, reviews or labels from dhh, ryanrhughes, spencerbull or acrogenesis. All six were closed by us.Silence is the signal. The ask has to become small.
How does a plugin become part of Omarchy?Elsewhen (#12157, 108 lines, merged without comment): a package in omacom's repos, installed under /usr/share/omarchy/shell/plugins/omacom.elsewhen, a 12-line migration that symlinks it into the user's plugin dir and puts it on the bar.This is the route. The code lives in a package; the PR to Omarchy is ~100 lines.
How does Omarchy use Docker?Users are not in the docker group (it is root-equivalent). omarchy-windows-vm, a single 1,614-line bash file, runs Docker behind one polkit prompt per action, re-executing itself as root, taking the user's identity from pkexec, and never trusting a user-writable file.Our backend is shaped like that script. Its posture is the one the security reviewer made us adopt anyway.
What does dhh think local models are?The manual defines AI as coding agents. Its "Local LLMs" section is two sentences (LM Studio, Ollama). On Ollama: "Not sure there's enough value there." He required an uninstaller for anything installed.Pitch it as "your coding agents on your own GPU", ship an uninstaller, keep it opt-in.
How does a bar panel get its data?Agents panel: a bash script writes one JSON file, the QML watches the file. Error and setup states are just two strings in that file.Our card already works this way. Keep it, drop everything else.
Coding rules?#!/bin/bash, one self-contained script per feature (no lib/), helper commands instead of raw pacman, tests as shimmed shell files with no real docker or network, logic in a Model.js that node can test.The tree in section 4.

Two conclusions that reshaped the plan

  • Small PR, big package. The thing we build is the plugin, made to look like Omarchy wrote it. The PR to Omarchy just adopts it.
  • Vendored recipes are the secure choice, not only the simple one. Root runs the container. Root must never build a docker run from a file the user could have swapped. A recipe fetched at runtime into your home is exactly such a file. A recipe that ships inside the package under /usr/share/omarchy is root-owned, so root can read it. That also deletes the whole hash-pinning layer the plugin carries today.

4. The new shape

  omarchy-local-ai/                      ← the repo IS the plugin, nothing else in it
  ├── manifest.json                      plugin manifest (schemaVersion 1, bar-widget)
  ├── Panel.qml          ~450 lines      THE CARD, design unchanged
  ├── Model.js           ~250 lines      the card's logic, testable with node
  ├── recipes.json                       the registry's export, verbatim, one GPU entry per line
  ├── bin/
  │   ├── omarchy-local-ai   ~850 lines  THE BACKEND, one file, shaped like omarchy-windows-vm
  │   ├── omarchy-install-ai-local       Install › AI entry (NVIDIA toolkit, first snapshot)
  │   └── omarchy-remove-ai-local        the uninstaller
  └── test/shell.d/*-test.sh             shimmed tests in Omarchy's own form (no real docker, no network)

  gone:  lib/ (13 files)  ui/ (two presentations)  native/  scripts/  integrations/  wiki/  *.py
About 1,600 lines of code and one data file, down from 3,884. The count falls out of the drop list; nothing was cut to hit a number.

How the pieces talk

   Panel.qml (the card)                        bin/omarchy-local-ai (the backend)
   ─────────────────────                       ──────────────────────────────────
   watches  ~/.local/state/omarchy/local-ai/snapshot.json   ◄── written by `snapshot` (a pure read)
   runs     omarchy-local-ai load <recipe> <gpu>            ──► detaches a worker: weights, then ONE root phase
   runs     omarchy-local-ai unload                          ──► ONE root phase
   runs     omarchy-local-ai agent <name>                    ──► opens the agent in a terminal on the model

   No socket, no daemon, no HTTP between them. One JSON file in, four verbs out.

6. How root and Docker work

Copied from omarchy-windows-vm, which is the one Docker feature Omarchy has merged and then hardened through security review.

  user                                                   root (only inside these three phases)
  ────                                                   ─────────────────────────────────────
  omarchy-sudo-docker ?  ── "no prompt needed" ──►  run the phase directly (sudoless Docker on)
        │
        │ "prompt needed"
        ▼
  pkexec /usr/bin/omarchy-local-ai __priv start <recipe-id> <gpu-key>
                                                         │ pin PATH and locale
                                                         │ who am I working for?  PKEXEC_UID → account → home (owned, not a symlink)
                                                         │ inputs: recipe id and gpu key, regex-checked; nothing else crosses
                                                         │ recipe: read from the packaged file, re-checked against a fixed policy
                                                         │   (digest-pinned image from ghcr.io/0xsero, no caps, no host ipc,
                                                         │    mounts only <home>/.cache/…/models/<id> read-only and /dev/dri read-only)
                                                         │ docker run engine (as the user's uid) + gateway on 127.0.0.1:12434
                                                         │ wait, accept (one real chat completion), rollback on failure
                                                         ▼
                                                   one prompt per Start, one per Stop, one for the NVIDIA toolkit
Weights download runs as the user with curl and sha256, never as root. The gateway key is read from a file, never expanded into a command line.

9. What does not change

  • The card's design. Same views, same rows, same actions. Only the share and update rows go, with their features.
  • The security posture the six review rounds forced: digest-pinned attested images, private networks, read-only confined mounts, key never in argv or logs, private state files. Each finding becomes a named test.
  • The registry as the only place a recipe is authored and validated.
  • The live plugin. v5.4.0 stays on the marketplace and on your machines until 6.0.0 is green on the box in prompt mode.

12. Security, layer by layer

Seven layers, each answering one question. The right-hand column is the review finding or Omarchy rule it comes from, so nothing here is a preference.

                       what can be trusted                              what is checked
  ┌──────────────────────────────────────────────────────────────────────────────────────────────┐
  │ 1  DATA        registry (validated on rented cards) ──► recipes.json shipped IN the package   │
  │                image digests + GitHub build attestations                                     │
  │      root-owned once packaged; content re-checked by policy at every use                     │
  ├──────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 2  PLUGIN      the card and the backend run as the user, unsandboxed (Omarchy's rule for      │
  │                every plugin); the bar hands a third-party widget a facade, not the real bar   │
  ├──────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 3  USER SIDE   weights: curl at the pinned revision, sha256 of every file vs the Hub tree     │
  │                state dir 0700, files 0600, written by mktemp + mv, snapshot ≤ 256 KiB         │
  │                secrets: gateway.key 0600, HF token in a header FILE; never argv, log, snapshot│
  ├────────────────────────────  the prompt (pkexec)  ───────────────────────────────────────────┤
  │ 4  BOUNDARY    target = canonical root-owned /usr/bin path (or the named plugin file)        │

Layers 1 and 4 are what changed with this redesign: the recipe is packaged, so root can read it without a hash on the command line; identity and paths come from pkexec and the account, not from a user-writable env file.
