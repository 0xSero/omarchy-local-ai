Local AI from first principles

Written 2026-09-22. Five nouns, two small machines, one contract. Every diagram here has fewer than nine boxes; if a real path needs more, the design is wrong, not the diagram.

1. The five nouns

Everything in the system is one of these, and each points at the next.

flowchart LR
  G["GPU
what is in the machine"] --> H["hardware id
the registry's name for it"]
  H --> R["recipe
the one validated way to run a model on it"]
  R --> S["run
weights on disk + two containers + one check"]
  S --> A["agent
a coding tool pointed at the run"]
The registry owns the first three. The plugin owns the last two. Nothing else exists.

2. The registry, reduced to its job

The registry has 813 models, 2,749 recipe records, 3,087 speed sweeps, prices and benchmarks. None of that is the plugin's business. The registry's job, seen from the plugin, is to answer one question:

Given a GPU name, what is the one validated recipe, and what exactly must run?

So the registry exports one file, and that file is the entire contract between the two repositories. Today it carries fields the launcher never reads, and fields the launcher must refuse (host IPC, extra capabilities, security options). From first principles the export should contain only what a launch consumes, so that what cannot be expressed cannot be refused.

Gone from the export: ipc, capAdd, securityOpt, networkMode, entrypoint, devices paths, free-form mounts, provenance text, validated, speed, concurrency, precision, tag. Mounts are not data at all: the launcher always mounts exactly the recipe's weights directory read-only, and the render nodes the user chose. The evidence (attestation, acceptance record, speed) stays in the registry where a human reads it. The export goes from about forty fields to about twenty, and the root-side policy check shrinks with it, because half of what it refused can no longer be written.

3. What a run is

A run is three facts that are either true or not: the weights are on disk and verified; the two containers exist; the gateway answered one real request. The plugin's job is to make them true in that order and to tell the truth about which are.

flowchart LR
  W["weights verified
(user, curl + sha256)"] --> C["containers up
(root, one prompt)"] --> K["accepted
(one real completion)"]
  K -- "no" --> U["undo: remove the new pair,
put the previous one back"]
One line, one undo. There is no other path.

4. The two machines

The card's state word is not a machine. It is a projection of these two.

stateDiagram-v2
  direction LR
  [*] --> none
  none --> download: load
  download --> start: verified
  download --> none: failed or cancelled
  start --> none: accepted, or failed with the previous run restored
  none --> stop: unload
  stop --> none: removed
Machine 1, the operation. At most one at a time, held by a lock. A failure is a sentence left behind, not a state.
stateDiagram-v2
  direction LR
  [*] --> absent
  absent --> ready: a start was accepted
  ready --> absent: stop
  ready --> aside: a new start on the same cards
  aside --> absent: the new one was accepted
  aside --> ready: the new one failed
Machine 2, a slot: one per GPU group. "Aside" is the previous run waiting to see whether it is still needed.
What the card shows = the operation if one is running; otherwise ready if any slot is ready; otherwise idle. Plus the last failure sentence, if any.

8. What has to change in the registry

One script, scripts/export_plugin_recipes.py, emits the smaller schema (omarchy-local-ai/recipes/2): drop the fields above, fold launch.mounts and launch.devices away, keep one optional asset per recipe. Its CI gate checks that every exported recipe is expressible, which it now is by construction. The plugin's make sync takes the result unchanged. Nothing about validation, evidence or the website changes.
