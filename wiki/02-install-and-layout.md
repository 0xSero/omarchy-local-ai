# 2 — Install and file layout

## Install

```bash
omarchy plugin add https://github.com/0xSero/omarchy-local-ai.git --enable
```

Omarchy clones the repository into `~/.config/omarchy/plugins/sero.local-ai` and enables it. `omarchy
plugin add` is a clone, which is why the traffic workflow counts clones as installs.

`manifest.json` is what Omarchy reads:

| Field | Value | Consequence |
|---|---|---|
| `schemaVersion` | `1` | manifest format |
| `id` | `sero.local-ai` | the plugin identifier; also the IPC target |
| `name` | `Local AI` | display name |
| `version` | `5.0.7` | must equal the release tag's version (`release.yml` checks it) |
| `kinds` | `["bar-widget"]` | it is a bar widget and nothing else |
| `activation` | `on-demand` | the QML is loaded when the widget is instantiated |
| `entryPoints.barWidget` | `ui/Panel.qml` | the QML root |
| `barWidget.category` | `AI` | marketplace category |
| `barWidget.aliases` | `local-ai`, `local-model`, `gpu` | bar search |
| `barWidget.defaultSection` | `right` | where the icon lands |
| `barWidget.allowMultiple` | `false` | one instance |

`bin/omarchy-local-ai` declares itself to Omarchy in its first two comment lines:

```
# omarchy:summary=Run the validated local models for this machine's GPUs and open coding agents on them
# omarchy:args=<snapshot|load|unload [recipe]|open-agent [name] [recipe]|share [--key value]|gpu [key]|recipe [id]|recipes [update]|agent-dir <path>>
```

## Requirements

| Thing | Needed for | Notes |
|---|---|---|
| `bash`, `jq`, `curl` | everything | missing `jq`/`curl` is reported on the card as `missing tool: jq (sudo pacman -S jq)` |
| `flock` (util-linux) | the op lock | without it a `mkdir` lock with a pid file is used; Omarchy always has util-linux |
| docker | everything that runs | no docker-group membership needed; see [1 — Architecture](01-architecture.md) |
| pkexec + a polkit agent | the prompt mode | Omarchy ships both |
| NVIDIA GPU (8 GB+) or Intel Arc Pro B70 | a recipe to exist for your card | the NVIDIA container toolkit is installed inside the same prompt when missing |
| `hf` | faster downloads | optional; without it the recipe's own image downloads |
| `tailscale` | `share` | optional |

The card says what is missing before it tries: with no supported GPU it reads *no supported GPU*;
with a GPU but no recipe for it, *no validated recipe for &lt;product&gt; yet*.

### The release bundle, and what a source archive holds

`make bundle` writes `dist/omarchy-local-ai-$(jq -r .version manifest.json).tar.gz` from an explicit
file list:

```make
RUNTIME = manifest.json recipes.json LICENSE bin/omarchy-local-ai $(wildcard lib/*.sh) $(wildcard ui/*.qml) ui/ui.js
```

`test/bundle` then builds it, asserts the archive contains **exactly** those files, unpacks it and
runs the whole suite against the unpacked copy — so what CI tests is what a release ships, not a
development checkout. A stray file added to the runtime list fails the test.

`.gitattributes` marks the development-only paths `export-ignore` (`/.github`, `/test`, `/docs`,
`/dist`, `/Makefile`, `/.gitignore`, `/.gitattributes`, and `/wiki`), so GitHub's source archives
carry the runtime set plus the repository's own `README.md`, `CHANGELOG.md` and listing images.
Installation itself is a clone (`omarchy plugin add`), which gets everything.

## What the plugin writes on your machine

Everything it owns is under three roots. Nothing else is touched — in particular nothing under
`~/.config`, and no agent config of yours.

### State: `~/.local/state/omarchy/local-ai/` (0700)

| File | Mode | Contents |
|---|---|---|
| `ledger.json` | 0600 | the only authoritative state: `.op`, `.error`, `.slots{}`, `.lastStartSeconds` |
| `snapshot.json` | 0600 | the derived read model the panel watches |
| `log` | 0600 | every worker step and every refusal, timestamped UTC. The libraries name it `$LOGFILE` — the token the quoted messages use |
| `gateway.key` | 0600 | the one secret (see [10 — Sharing](10-sharing.md)) |
| `gateway.auth` | 0600 | the `Authorization: Bearer …` header curl reads with `-H @file` |
| `slots/<recipe-id>.json` | 0600 | the recipe each running model was started from (read back for the card even if the file no longer lists it) |
| `gateway.recipe.json` | 0600 | every slot's recipe in one array; what a gateway restart republicates |
| `recipe.json` | 0600 | the recipe of the operation in flight; root reads this one |
| `root.env` | 0600 | the paths handed to a root phase, plus a hash pin |
| `phase.out`, `gate.err`, `accept.err`, `agent.err` | 0600 | the last stdout/stderr of the corresponding stage |
| `weights/<recipe-id>.json` | 0600 | the completion marker (see [6 — Weights](06-weights.md)) |
| `trees/<repo>@<rev>.tsv` | 0600 | cached Hub file trees, used for verifying weights you already have |
| `usage.jsonl` | 0600 | one line per request the plugin itself made through a gateway |
| `recipes.json` | 0600 | the fetched registry copy, when one is newer than the vendored file |
| `recipes.checked` | 0600 | unix time of the last refresh attempt (the TTL clock) |
| `share.on` | 0600 | present while sharing is wanted; holds the address published |
| `share.error` | 0600 | the last share refusal, shown under the toggle |
| `op.lock`, `ledger.lock`, `op.lockd/`, `ledger.lockd/` | 0600 | lock targets |
| `gpu`, `recipe-pick`, `agent-dir` | 0600 | your picks and settings |
| `agents/<name>/models.json`, `agents/<name>/config.yml`, `agents/crush/crush.json` | 0600 | per-agent launch config, generated at launch (see [9 — Agents](09-agents.md)) |
| `agents/args/<name>` | 0600 | NUL-separated extra flags for one agent |
| `assets/<file>` | 0644 | config assets from `recipes.json`, mounted read-only into the engine |
| `cancel` | 0600 | present while a download is being cancelled |

`state_dir()` re-asserts the directory mode and the file modes on every call, and `chmod -R go-rwx`
the `agents` tree, because the agent configs embed the key. It is also the migration path: an older
install whose `ledger.json` was 0644 gets tightened on the next snapshot.

### Model weights: `~/.cache/omarchy/local-ai/models/` and `~/.cache/omarchy/local-ai/cache/`

Two roots, both with the ordinary umask (`mkdir_shared`) because the engine container's uid must be
able to traverse them. `${MODEL_ROOT}` is where downloads land for local-dir recipes;
`${CACHE_ROOT}` is the second permitted root for recipes that mount it. Recipes may also mount
`~/.cache/huggingface` (hub layout).

### Nothing else

The plugin does not edit `~/.claude.json`, `~/.codex/`, or any other agent configuration. Agent
endpoints are passed in the launch command's environment, and the per-agent config files it *does*
write live under `$STATE/agents/` and are pointed at with environment variables such as
`PI_CODING_AGENT_DIR` and `XDG_CONFIG_HOME`. The suite asserts no user config file appears.

## Remove

```bash
omarchy-local-ai unload            # stops the models, keeps the downloads
omarchy plugin remove sero.local-ai
rm -rf ~/.cache/omarchy/local-ai ~/.local/state/omarchy/local-ai   # optional
```

Removing the plugin does not stop containers by itself: run `unload` first. If a container is left
behind, `docker rm -f $(docker ps -aq --filter label=io.omarchy.local-ai=1)` removes exactly the
plugin's containers and nothing else.
